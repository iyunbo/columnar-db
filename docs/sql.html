SQL Frontend

Hand-rolled lexer, recursive-descent parser, and query planner. No external parser generators.

Pipeline

SQL string ↓ Tokenize() Token stream ↓ Parse() AST (SelectStmt) ↓ Plan() Operator tree ↓ drain Next() Results

Lexer

Single-pass, allocation-free tokenizer. Scans the SQL string left-to-right, emitting tokens for keywords, identifiers, numbers, strings, and operators.

Tokens: SELECT, FROM, WHERE, GROUP, BY, ORDER, ASC, DESC, LIMIT, AS, identifiers, numbers, quoted strings, comparison operators, *, ,, (, ).

Parser

Hand-rolled recursive-descent parser. Produces a SelectStmt AST:

type SelectStmt struct {
    Items    []SelectItem    // columns or aggregates
    Table    string          // FROM table
    Where    *Predicate      // optional WHERE
    GroupBy  []string        // optional GROUP BY columns
    OrderBy  *OrderByClause  // optional ORDER BY
    Limit    *int            // optional LIMIT
}

Planner

Translates the AST into an operator tree. The planner picks the right operators based on what the query needs:

Query patternOperator tree
Simple selectScan → [Filter] → [Project]
Aggregate (no GROUP BY)Scan → [Filter] → Aggregate
GROUP BYScan → [Filter] → GroupBy
+ ORDER BY… → OrderBy
+ LIMIT… → Limit

Supported SQL

SELECT { * | col [, ...] | agg(col) [, ...] }
FROM table
[WHERE col { = | != | < | <= | > | >= } literal]
[GROUP BY col [, col ...]]
[ORDER BY col [ASC | DESC]]
[LIMIT n]

Aggregates: COUNT(*), COUNT(col), SUM, MIN, MAX, AVG.

Performance

SQL overhead vs direct operator API calls (with statement reuse via Reset):

ScenarioOverhead
Low cardinality+0.3%
High cardinality+3.8%

The SQL layer adds negligible overhead because the planner builds the same operator tree you'd build by hand.

Known Limitations

  • No AND / OR in WHERE (single predicate only)
  • No HAVING, JOIN, subqueries, or DISTINCT
  • Single table only
  • No expression evaluation in SELECT (e.g. col + 1)
